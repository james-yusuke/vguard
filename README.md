# VGuard

English · [日本語](README-JA.md)

VGuard traces failures in binaries generated by V back to the V source. For direct amd64, arm64,
and WebAssembly builds, it also reports the SSA value ID and opcode.

## Setup

### Install with VPM

With `v` and Git on your `PATH`, install the VGuard sources from GitHub and build the CLI
from the installed package.

```sh
v install --git https://github.com/james-yusuke/vguard
vguard_src="$(v env VMODULES)/vguard"
v -o vguard "$vguard_src"
./vguard --help
```

If VPM reports a different install directory, use the path it prints for `vguard_src`.
You can also run the CLI directly with `v run "$vguard_src" --help`.

### Build VGuard

From a Git checkout, run these commands from the repository root. Use `.` as the
compilation target because VGuard spans multiple `.v` files.

```sh
v run . --help
v -o vguard .
```

### Build the target compiler

`vguard build --v` requires a V compiler that can emit VGuard source maps. Apply the bundled
[VGuard patch](compiler/vguard.patch) to the sibling `../v` checkout and rebuild the compiler.
The patch is based on revision `323045464d07c3f6e426f994cfbfe6cfb365ae84`.
For a VPM install, the patch is at `$vguard_src/compiler/vguard.patch`. Apply it in the V compiler
checkout you plan to use with `--v`.

```sh
# Apply the patch if it has not been applied.
git -C ../v apply --check ../vguard/compiler/vguard.patch
git -C ../v apply ../vguard/compiler/vguard.patch

(cd ../v && ./v -all-backends self)
```

In addition to V's usual build dependencies, `run` uses GDB on Linux, LLDB on macOS and Windows,
and the Wasmtime CLI for WebAssembly. C and FastC source lookup uses `llvm-symbolizer`.
The WebAssembly reference build uses Emscripten's `emcc`. Pass
`--v-arg -cc --v-arg /path/to/emcc` at build time to use the same C compiler for the reference build.

## Usage

Run VGuard without arguments to list the commands. Pass a V file or directory to `build`, then
pass the generated `build.json` to `run` or `compare`. You can use `v run .` in place
of `./vguard`.

Try the [crash detection and memory check examples](examples/README.md).

On Apple Silicon, for example, run these commands from the repository root.

```sh
./vguard build ./app --v ../v/v --backend arm64 --target macos/arm64 --out ./guard-build
./vguard run ./guard-build/build.json --case ./case.json
./vguard compare ./guard-build/build.json --case ./case.json --json
```

Choose a new directory for `--out`. Pass compiler arguments individually, as in
`--v-arg -cc --v-arg clang`. Use `--prod` for optimized builds.

Both `run` and `compare` accept a JSON case file.

```json
{
  "argv": ["sample"],
  "stdin": "7\n",
  "cwd": ".",
  "env": {"LANG": "C"},
  "timeout_ms": 30000
}
```

Relative paths are resolved from the directory containing the case file. For a shared library,
set `harness` to the executable to launch and have it load the library at the path in
`VGUARD_ARTIFACT`.

Use `resolve` to look up a recorded address or offset.

| Recorded location | Arguments |
|---|---|
| Runtime PC and actual image load address | `--pc 0x... --load-base 0x...` |
| Link-time virtual address or PE RVA | `--address 0x...` |
| Offset in an ELF, Mach-O, or COFF object section | `--section 1 --offset 0x...` |
| Byte offset in a WebAssembly module or a `-hot-fn` function | `--offset 0x...` |

`resolve`, `run`, and `compare` show a source excerpt in the terminal when a source location
is available. The `^` marker points to the reported column, or `>` marks the line when only
a line number is known. Use `--json` for machine-readable output. Exit code 0 indicates
success, 1 indicates a crash or a difference, and 2 indicates a tool error or an inconclusive result.

For direct amd64, arm64, and WebAssembly builds, `run` prints the mapped SSA function twice.
The compiler uses the same formatter for snapshots and the amd64 `V_X64_DUMP_SSA` debug dump.
The annotated copy appends `<<` and the stop reason to the mapped instruction. If the debugger
found a V caller frame, the annotation identifies that frame. `run` also saves the full dumps
in `diagnostics/crash-…/` inside the build directory.

| File | JSON field |
|---|---|
| `original.ssa` | `ssa_original_file` |
| `crash.ssa` with the inline annotation and crash details | `ssa_file` |

Apply the updated patch to a clean checkout of the pinned V revision, rebuild the compiler,
and rebuild the target to produce this dump format. Existing build directories retain the
previous snapshot format. The JSON report records SSA read or write errors in `ssa_error`.

Use `--ssa` to write the full annotated V SSA to standard output. Diagnostic details are SSA
comments. When no instruction can be mapped, the output contains the diagnostic comments
alone. The target's output goes to standard error in this mode.

```sh
./vguard run ./guard-build/build.json --ssa > report.ssa
```

### Trace native compilation

Add `--trace-build` to a direct `amd64` or `arm64` build. For example, on Apple Silicon,
run this command from the repository root with the patched target compiler.

```sh
./vguard build examples/crash.v --v ../v/v --backend arm64 --target macos/arm64 \
  --trace-build --out ./trace-build --v-arg -gc --v-arg none
```

VGuard forwards compiler output to standard error during the build. The output directory
contains these files, including when the compiler fails.

| File | Contents |
|---|---|
| `compile-trace.json` | Original stage labels, durations, RSS, and elapsed compiler time |
| `compiler.stdout.log`, `compiler.stderr.log` | The compiler's captured output streams |

The JSON follows the order in which V reported the stages with `-show-timings`.
Parallel work can make stage durations overlap. A successful VGuard build also writes
`build.json` for `run`, `resolve`, and `compare`.

## SSA analysis and recorded executions

Rebuild the pinned V compiler with the updated [companion patch](compiler/vguard.patch).
Use `--trace-ssa` when building with amd64, arm64, or Wasm. Add `--prod` to
observe the production SSA optimizer.

```sh
./vguard build examples/crashes/rounded_divisor.v --v ../v/v-vguard \
  --backend wasm --target wasm32_emscripten/wasm32 --prod --trace-ssa --out ./ssa-analysis
./vguard run ./ssa-analysis/build.json --dataflow
```

The build directory contains `program.vgmap.json.passes.jsonl` and
`program.vgmap.json.passes.jsonl.graph.json`. The pass log starts with a baseline and
records instruction IDs added, changed, or removed between checkpoints. Rewrite
events name each user whose operand the optimizer replaced. Verifier findings
retain the compiler's critical and advisory classification and the checkpoint
records whether verification ran. A skipped optimizer still emits a graph and
records the reason. The manifest stores checksums for both files.

The pass log and final graph include an optional `ast` field for instructions
with a recorded origin in the lowered AST used to build SSA. It includes the
node ID and kind, the reported file, line and column, and a half-open byte range
in `source_file`. The reported file can differ from the source file when a
`#line` directive applies. Node IDs are local to the compilation. When the
inliner copies an instruction with a recorded origin, `copied_from` gives the
original SSA value ID. Instructions generated without a recorded origin omit
`ast`.

`run --dataflow` follows SSA operands, phi inputs, lowered phi copies, and
predecessor branches from the mapped stop. Results in `ssa_dataflow` describe
static candidates. The terminal report shows the mapped instruction's AST origin
when available. Add `--json` to inspect the AST origins of upstream instructions
as well. The walk examines at most 128 instructions and reports truncation.
Runtime branch selection and memory aliasing are outside this analysis.

`run --stack` captures the native debugger's all-thread backtrace at a fatal stop.
The `stack_trace` field includes debugger output with the frames, arguments, and
source locations it could recover. Argument and source information depend on the
binary's debug metadata. The optional `threads` array groups recognized frames
by debugger thread number. Frame arguments are preserved as debugger text, and
source file, line, and column are reported when printed by the debugger.
Wasm and sanitizer reports can use their existing
stack information.

Compare two existing build manifests with `compare --reference other/build.json`
to run the two binaries with the same case. The report includes build identities
and the first differing byte in stdout and stderr. For a reproducible difference,
VGuard also attempts to compare scalar checkpoints when both manifests point to
the same source and their original compiler binaries are available.

Use `regress` to locate the first observed output change in an ordered series of
existing builds. List the baseline first. Manifest paths are relative to the series file.

```json
{
  "builds": [
    {"label": "baseline", "manifest": "baseline/build.json"},
    {"label": "candidate", "manifest": "candidate/build.json"}
  ]
}
```

Run `./vguard regress ./series.json --case ./case.json --json`. The builds must
share a source fingerprint. VGuard checks stdout and stderr twice per build
and follows the listed order. It reports `changed` at the first reproducible
difference or `inconclusive` at an unstable or unsuccessful execution. Exit codes
are 0 for `unchanged`, 1 for `changed`, and 2 for `inconclusive` or an error.

`record <build.json> --out <new-directory>` records scalar assignments, branches,
and returns from a standalone program with a successful, matching baseline.
`record --calls` also records named V function entries in the instrumented source
file or the top-level source files of the build directory. Update the compiler
patch and rebuild the compiler and target before using this option.
`replay <new-directory>/history.json` reads those recorded events offline in order.
Use the existing `--case` option with `record` to select inputs.

`minimize` tries line deletions in a copy of a common, single V source file.
It requires two existing builds whose compiler and source fingerprints still match
their manifests and whose successful outputs are repeatable and different.

```sh
./vguard minimize ./candidate/build.json --reference ./baseline/build.json \
  --case ./case.json --out ./reduced --attempts 32
```

The output directory contains the reduced `.v` file and `reduction.json`.
Both configurations are rebuilt and run twice to verify the final result.
`single_line_deletions_checked` indicates whether the search checked all single-line
deletions in its final candidate. A nonzero exit or runtime interruption stops reduction.

Run `python3 benchmarks/ssa_trace.py --help` for the build-time benchmark. It
measures elapsed time, trace size, and equality of emitted binary bytes.

The current diagnostics cover the SSA pipeline and selected runtime observations.
CPU register and stack-slot mappings, native Shadow Memory, instruction-level
memory replay, and deadlock classification remain outside this implementation.

### WebAssembly execution limits

`run --fuel 100000` configures a Wasmtime fuel budget. The report distinguishes a
Wasmtime fuel trap, identified as `fuel_exhausted`, from a VGuard wall-clock `timeout`.
Both return exit code 2. The JSON `execution_limit` includes the configured limit and
its evidence source. A fuel trap includes the Wasm address and mapped source location
when available. If the address falls inside a mapped function but outside all SSA
ranges, the report identifies the function body. Fuel measures Wasmtime's execution budget, so exhaustion can occur
during finite computation. [Wasmtime fuel accounting](https://docs.wasmtime.dev/api/wasmtime/struct.Store.html#method.set_fuel)

## Memory safety checks

Build a standalone executable with the C backend and `--memory`, then run it with the
same JSON case format. On macOS/arm64, for example, use these commands from the repository root.

```sh
./vguard build ./app --v ../v/v-vguard --backend c --target macos/arm64 --memory --out ./guard-memory
./vguard run ./guard-memory/build.json --case ./case.json --json
```

The normal debugger path observes stops and cannot see an invalid access that leaves the process
running. A memory build uses Clang AddressSanitizer for checks on heap, stack, and global accesses,
heap use-after-free, double free, and invalid free. Clang UndefinedBehaviorSanitizer checks
null dereferences and array bounds that Clang can determine. VGuard reads sanitizer diagnostics
independently of the process exit status. The checks can report a violation before a CPU fault.
[AddressSanitizer](https://clang.llvm.org/docs/AddressSanitizer.html) ·
[UndefinedBehaviorSanitizer](https://clang.llvm.org/docs/UndefinedBehaviorSanitizer.html)

`run` returns exit code 1 and `kind: "memory_error"` when it finds a supported violation.
The `memory_errors` entries include the kind, address, operation, size, and V source location
when available. Allocation and deallocation locations are included when the sanitizer supplies
those stacks and their V frames can be resolved. ASan overflow reports distinguish reads and
writes. UBSan array bounds reports can omit the operation and address.

`--memory` selects Clang and `-gc none`. It supports Linux/amd64, Linux/arm64, and macOS/arm64
with a matching host, Clang, and its sanitizer runtimes. Source lookup uses `llvm-symbolizer`,
`addr2line` on Linux, or `atos` on macOS. Memory reports use C backend debug information, so SSA
IDs are unavailable in this mode. The ordinary native and WebAssembly crash paths still provide
SSA lookup. FastC, direct native and WebAssembly builds, Windows, and shared-library harnesses
are outside the memory mode's coverage.

Coverage depends on the paths exercised by the case. Assembly, uninstrumented libraries, custom
allocators without ASan support, and accesses that remain inside a valid allocation can escape
detection. Use-after-free detection also depends on the allocator's quarantine and reuse.

## Diagnostic coverage

- Direct ELF generation covers Linux/amd64 and Linux/arm64. Direct Mach-O generation covers
  macOS/arm64. Use `--object` for object files and `--hot-fn <symbol>` for raw arm64 code.
- For ELF, Mach-O, and PE/COFF produced by C or FastC, VGuard resolves V line numbers from
  debug information. FastC object builds require `--v-arg -cc --v-arg clang`. Keep PE `.pdb`
  files and Mach-O `.dSYM` bundles with the build artifacts.
- VGuard checks the source map against the artifact's SHA-256 digest. When a location cannot be
  resolved, VGuard reports the reason, such as a missing instruction mapping or debug information.
- `compare` first compares the results without tracing. On a difference, it reruns both builds
  with tracing for scalar assignments, branch conditions, and return values. FastC traces boolean
  conditions and integer and boolean literals. The reported location is the first observed
  divergence. The original output difference stays in the report if rebuilding or reproducing it
  fails due to types, control flow, or external I/O.

Run `v test .` to check source map validation, address boundaries, debugger output
parsing, and trace comparisons. Set `VGUARD_TEST_COMPILER=../v/v` to also run integration tests
with the rebuilt compiler. If `wasmtime` is on `PATH`, the integration tests also cover
WebAssembly traps.

## GitHub contribution and CI

Use the issue forms for a [bug report](.github/ISSUE_TEMPLATE/bug_report.yml) or
[feature request](.github/ISSUE_TEMPLATE/feature_request.yml).
The [Pull Request template](.github/PULL_REQUEST_TEMPLATE.md) provides space for the change,
checks, and an example.

The [CI workflow](.github/workflows/ci.yml) runs on Pull Requests and pushes to `main`, and can
also be started from the Actions tab. On Linux/amd64, Linux/arm64, and macOS/arm64, it checks
formatting, runs unit and integration tests, and validates the crash and memory check examples.
Successful jobs upload the VGuard binary archive, JSON reports, and the crash SSA.

In a Pull Request, open **Checks** or run `gh pr checks --watch` to follow its jobs.
